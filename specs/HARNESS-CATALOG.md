# HARNESS-CATALOG.md — 외부 하네스 카탈로그 (선택적 부착, 조건부)

> **이 문서는 형식·룰 명세 문서.** 에이전트 룰북 아님.
> **하네스(harness)** = 이 프레임워크를 *바깥에서 감싸 구동하는* 별도 시스템. 프레임워크 안쪽 규칙을 바꾸는 것이 아니라, *언제·누구의 정체성으로·어디서* 오케스트레이터 세션이 뜨는지를 바깥에서 정한다. 각 하네스는 **별도 레포**로 살고, 본 카탈로그는 그 **목록**만 갖는다.
> 본 카탈로그는 **조건부** 다 — 하네스 없이 운영하는 시스템이 기본이고 정상이다(범용 전제). 어느 하네스도 요구사항이 아니다.
> ⚠️ **`templates/extensions/`(AWS 레포 룰 확장)와 다른 것** — §1.2. 이름을 섞어 쓰지 말 것.
> 변경은 깃 PR/머지 (원칙 8) — `agents/SETTER.md`(S5.9 인터뷰 / S9.5 안내)·`templates/ORCHESTRATOR.template.md`(「부착된 하네스」 섹션)가 본 카탈로그에 연계되므로 변경 시 영향 검토.
> 위치: `ai-dlc-orchestrator/specs/HARNESS-CATALOG.md`

## 1. 정체성 / 부착 규율

| 항목 | 내용 |
|---|---|
| 종류 | 형식·룰 명세 문서 (에이전트 X) — **레지스트리(목록)** |
| 참조 주체 | `agents/SETTER.md` S5.9(사용 여부 인터뷰)·S9.5(최초 설치자 안내) / `templates/ORCHESTRATOR.template.md`(부착 결과 기록) |
| 소비 시점 | 부트스트랩 인터뷰(S5.9)와 검증 이후·종료 이전(S9.5). 운영 중에는 사람이 직접 읽고 붙여도 된다 |
| 위치 | `ai-dlc-orchestrator/specs/HARNESS-CATALOG.md` |

### 1.1 프레임워크는 하네스를 *알지* 못하고 *목록만* 갖는다

**온보딩 지식(설치 절차·config 스키마·자격증명·운영법)은 각 하네스 레포가 소유한다.** 본 카탈로그는 그 레포로 가는 *포인터*(무엇인지·어디 있는지·어떻게 들어가는지·전제가 무엇인지)만 적는다.

- **이유**: 하네스의 config 스키마가 바뀔 때마다 이 프레임워크에 PR이 필요해지면 안 된다(원칙 8 마찰). 절차를 여기 복제하면 즉시 낡고, 두 원천이 갈라진다(원칙 6 — 단일 원천).
- **따라서 SETTER는 하네스를 *실행하지 않는다*.** 카탈로그 행을 *그대로 전달*할 뿐이고, 실제 온보딩은 그 하네스 레포의 진입점이 수행한다.
- **행 추가만으로 하네스가 늘어난다** — 새 하네스는 §2 표에 한 행을 더하면 끝이고, SETTER·템플릿·오케스트레이터 룰북은 손대지 않는다.

### 1.2 `templates/extensions/`와 다르다 (이름 충돌 주의)

| | **하네스** (본 문서) | **Extension** (`templates/extensions/`) |
|---|---|---|
| 무엇 | 프레임워크를 *바깥에서 구동*하는 외부 시스템 | *레포 안쪽* AWS AI-DLC 룰 확장 (`quality`·`coding`·`framework`) |
| 사는 곳 | **별도 레포** (본 리포 밖) | 본 리포 `templates/extensions/` |
| 붙이는 주체 | 사람 — 하네스 레포의 진입점 (SETTER는 *안내만*) | `REPO-SETTER` (RP6) — 레포마다 설치 |
| 스코프 | 시스템 바깥 (실행 트리거·정체성·호스팅) | 레포 안 (STEP 4 코드 생성 시점 규칙) |

두 개념은 **무관하다.** "extension"이라는 말은 후자에만 쓴다.

## 2. 카탈로그 (행 추가만으로 늘어난다)

| 하네스 | 무엇을 하나 | 레포 URL | 진입 방법 | 최초 설치자 경로 | 합류자 경로 | 전제조건 |
|---|---|---|---|---|---|---|
| `jira-auto-dispatcher` | Jira 티켓이 사용자에게 할당되면 **그 사용자 정체성으로** 이 프레임워크의 오케스트레이터를 컨테이너에서 자율 실행한다 (티켓 → 자율 세션) | `https://github.com/yunhyuk-choi/jira-auto-dispatcher` | 클론 후 `python -m app.setup wizard` (대화형 설치 — 에이전트 런타임 없이도 동작). `python -m app.setup skill` 로 슬래시 커맨드 `/install-jira-auto-dispatcher` 를 로컬에 설치할 수도 있다 (`.claude/` 는 개인 영역이라 추적하지 않고 생성기가 만든다) | 위 마법사를 돌려 배포한다. **검증된 `dlc-meta` 공유 원격 URL** 을 입력으로 받는다. 산출된 **대시보드(관리 UI) URL** 을 시스템 인스턴스에 기록한다 (SETTER S9.5) | **로컬 설치 없음.** 인스턴스에 기록된 대시보드에서 자기 자격증명을 등록한다. ⚠️ 합류 완성은 **로컬 SETTER 합류 + 대시보드 등록 2단** — 한쪽만으로는 티켓이 그 사람 이름으로 돌지 않는다 | Docker + Compose v2 / Jira **Cloud** (Server·DC 미지원) / `dlc-meta` 공유 원격이 **배포 호스트에서 도달 가능**할 것 |

> 위 값은 *그 하네스 레포가 공표한 사실*이고, 상세·최신은 언제나 레포가 원천이다. 여기 적힌 것과 레포가 어긋나면 **레포가 맞다** — 카탈로그 행을 PR로 고친다.

## 3. 행 스키마 (새 하네스를 추가할 때)

새 하네스는 §2 표에 **아래 7열을 채운 한 행**을 더한다. 그 이상 쓰지 않는다 — 설치 절차·옵션·트러블슈팅은 하네스 레포 몫이다(§1.1).

| 열 | 무엇을 적나 | 적지 않는 것 |
|---|---|---|
| 하네스 | 식별자(레포명) | — |
| 무엇을 하나 | 한두 문장. *왜 붙이는지*가 보이게 | 아키텍처 설명 |
| 레포 URL | 온보딩 지식의 단일 원천 | — |
| 진입 방법 | 클론 후 실행할 **진입점 한 줄** (마법사·설치 커맨드 등) | 옵션·플래그 전량, config 스키마 |
| 최초 설치자 경로 | 팀에서 처음 붙이는 사람이 할 일 + **인스턴스에 기록할 좌표**(대개 대시보드 URL) | 단계별 절차 복제 |
| 합류자 경로 | 이미 도는 하네스에 사람이 합류할 때 할 일 (대개 *로컬 할 일 없음* + 대시보드 등록) | — |
| 전제조건 | 없으면 붙일 수 없는 것 (런타임·플랫폼 제약·도달성) | 권장 사양 |

**금지**: 토큰·키·엔드포인트 등 **배포별 구체값**을 카탈로그에 박지 않는다. 그런 값은 인스턴스(Layer 1) 또는 머신 로컬 시크릿에 산다 (자격증명 경계 / POLICY-TRACKING).

## 4. SETTER 연계 (두 지점) — 요약

상세는 `agents/SETTER.md`. 여기서는 본 카탈로그가 *어디서 소비되는지*만 정리한다.

| 지점 | 하는 일 | 조건부 |
|---|---|---|
| **S5.9** (인터뷰 페이즈) | "하네스를 쓸 건가 · 어느 것인가"만 수집. 다른 인터뷰가 전부 그 자리에 있으므로 일관된다 | "아니오"면 S9.5까지 통째로 스킵 |
| **S9.5** (검증 S9 이후 · 종료 S10 이전) | 선택했고 **팀 최초 설치자면** 그 하네스 온보딩으로 안내. 성사 시 대시보드 좌표를 인스턴스에 기록·커밋 | 합류자는 **no-op** |

**S9 이후에 두는 이유 (배치 근거)**:
1. 하네스 온보딩은 **`dlc-meta` 공유 원격 URL이 확정·검증된 상태**를 입력으로 받는다 — 그 검증이 끝나는 곳이 S8.6(push)·S9(체크)다.
2. S9 뒤라는 것은 **하네스 온보딩이 실패해도 코어 부트스트랩은 이미 성사**됐다는 뜻이다. 실패가 부트스트랩으로 번지지 않게 격리된다 — EX-15와 같은 사상(**C FALLBACK**, 중단 금지. `agents/orchestrator/ERROR-POLICY.md` §1).

**최초/합류 판정은 묻지 않는다** — SETTER Q2.4가 *원격에 인스턴스가 있느냐*로 신규/합류를 가르는 것과 같은 방식으로, **시스템 인스턴스에 그 하네스의 대시보드 좌표가 기록돼 있느냐**로 가른다.

| 인스턴스 「부착된 하네스」 섹션 | 판정 | 행동 |
|---|---|---|
| 해당 하네스 기록 **있음** | 팀에서 이미 돌고 있다 | **no-op** — 합류자는 로컬에서 할 일이 없다. 기록된 대시보드로 가면 된다 |
| 기록 **없음** | 아직 아무도 안 붙였다 → **최초 설치자** | 카탈로그 행 그대로 안내 → 성사 시 좌표 기록·커밋·push |

기록이 커밋되면 **합류자는 clone만으로 그 값을 손에 넣는다** — 입력도 안내도 불필요하다. 그래서 최초 설치자의 기록·push 성사가 중요하다 (POLICY-TRACKING).
