# HARNESS-CATALOG.md — 외부 하네스 카탈로그 (선택적 부착, 조건부)

> **이 문서는 형식·룰 명세 문서.** 에이전트 룰북 아님.
> **하네스(harness)** = 이 프레임워크를 *바깥에서 감싸 구동하는* 별도 시스템. 프레임워크 안쪽 규칙을 바꾸는 것이 아니라, *언제·누구의 정체성으로·어디서* 오케스트레이터 세션이 뜨는지를 바깥에서 정한다. 각 하네스는 **별도 레포**로 살고, 본 카탈로그는 그 **목록**만 갖는다.
> 본 카탈로그는 **조건부** 다 — 하네스 없이 운영하는 시스템이 기본이고 정상이다(범용 전제). 어느 하네스도 요구사항이 아니다.
> ⚠️ **`templates/extensions/`(AWS 레포 룰 확장)와 다른 것** — §1.2. 이름을 섞어 쓰지 말 것.
> 변경은 깃 PR/머지 (원칙 8) — `agents/SETTER.md`(S5.9 인터뷰 / S9.5 **위임 실행**)·`templates/ORCHESTRATOR.template.md`(「부착된 하네스」 섹션)가 본 카탈로그에 연계되므로 변경 시 영향 검토.
> 위치: `ai-dlc-orchestrator/specs/HARNESS-CATALOG.md`

## 1. 정체성 / 부착 규율

| 항목 | 내용 |
|---|---|
| 종류 | 형식·룰 명세 문서 (에이전트 X) — **레지스트리(목록)** |
| 참조 주체 | `agents/SETTER.md` S5.9(사용 여부 인터뷰)·S9.5(최초 설치자 **위임 실행** — 클론 + 온보딩 룰북을 서브로 로드) / `templates/ORCHESTRATOR.template.md`(부착 결과 기록) |
| 소비 시점 | 부트스트랩 인터뷰(S5.9)와 검증 이후·종료 이전(S9.5). 운영 중에는 사람이 직접 읽고 붙여도 된다 |
| 위치 | `ai-dlc-orchestrator/specs/HARNESS-CATALOG.md` |

### 1.1 프레임워크는 하네스를 *알지* 못하고 *목록만* 갖는다

**온보딩 지식(설치 절차·config 스키마·자격증명·운영법)은 각 하네스 레포가 소유한다.** 본 카탈로그는 그 레포로 가는 *포인터*(무엇인지·어디 있는지·어떻게 들어가는지·전제가 무엇인지)만 적는다.

- **이유**: 하네스의 config 스키마가 바뀔 때마다 이 프레임워크에 PR이 필요해지면 안 된다(원칙 8 마찰). 절차를 여기 복제하면 즉시 낡고, 두 원천이 갈라진다(원칙 6 — 단일 원천).
- **프레임워크는 절차를 복제하지 않고 *위임*한다.** S9.5가 「레포 URL」로 하네스 레포를 **클론**하고 「온보딩 룰북 경로」의 룰북을 **서브 에이전트에 실어** 띄운다 — 설치 대화·config·트러블슈팅·*사용자에게 남는 수동 작업 안내*는 전부 그 룰북이 수행한다. 하네스가 절차를 바꿔도 이 리포는 그대로다(바뀔 수 있는 것은 카탈로그 행의 *포인터 한 줄*뿐).
- **행 추가만으로 하네스가 늘어난다** — 새 하네스는 §2 표에 한 행을 더하면 끝이고, SETTER·템플릿·오케스트레이터 룰북은 손대지 않는다.

### 1.2 `templates/extensions/`와 다르다 (이름 충돌 주의)

| | **하네스** (본 문서) | **Extension** (`templates/extensions/`) |
|---|---|---|
| 무엇 | 프레임워크를 *바깥에서 구동*하는 외부 시스템 | *레포 안쪽* AWS AI-DLC 룰 확장 (`quality`·`coding`·`framework`) |
| 사는 곳 | **별도 레포** (본 리포 밖) | 본 리포 `templates/extensions/` |
| 붙이는 주체 | **오케스트레이터** — 하네스 레포를 클론해 그 레포의 온보딩 룰북을 *서브로 위임 실행* (SETTER S9.5) | `REPO-SETTER` (RP6) — 레포마다 설치 |
| 스코프 | 시스템 바깥 (실행 트리거·정체성·호스팅) | 레포 안 (STEP 4 코드 생성 시점 규칙) |

두 개념은 **무관하다.** "extension"이라는 말은 후자에만 쓴다.

## 2. 카탈로그 (행 추가만으로 늘어난다)

| 하네스 | 무엇을 하나 | 레포 URL | **온보딩 룰북 경로** (레포 루트 기준) | 진입 방법 | 최초 설치자 경로 | 합류자 경로 | 전제조건 |
|---|---|---|---|---|---|---|---|
| `jira-auto-dispatcher` | Jira 티켓이 사용자에게 할당되면 **그 사용자 정체성으로** 이 프레임워크의 오케스트레이터를 컨테이너에서 자율 실행한다 (티켓 → 자율 세션) | `https://github.com/yunhyuk-choi/jira-auto-dispatcher` | `skill-templates/install-jira-auto-dispatcher/SKILL.template.md` | `python -m app.setup wizard` (대화형 설치 — 위 룰북이 태우는 대상. 에이전트 런타임 없이도 동작). `python -m app.setup skill` 로 슬래시 커맨드 `/install-jira-auto-dispatcher` 를 로컬에 설치할 수도 있다 (`.claude/` 는 개인 영역이라 추적하지 않고 생성기가 만든다) | 위 온보딩 룰북이 설치를 진행한다. **검증된 `dlc-meta` 공유 원격 URL** 을 입력으로 받는다. 산출된 **대시보드(관리 UI) URL** 을 시스템 인스턴스에 기록한다 (SETTER S9.5-b) | **로컬 설치 없음.** 인스턴스에 기록된 대시보드에서 자기 자격증명을 등록한다. ⚠️ 합류 완성은 **로컬 SETTER 합류 + 대시보드 등록 2단** — 한쪽만으로는 티켓이 그 사람 이름으로 돌지 않는다 | Docker + Compose v2 / Jira **Cloud** (Server·DC 미지원) / `dlc-meta` 공유 원격이 **하네스가 실제로 실행되는 런타임 컨텍스트에서 도달 가능**할 것 (컨테이너로 도는 하네스면 *그 컨테이너 안*에서. 일반 HTTPS 원격이면 호스트·컨테이너 모두 되므로 대개 자동 충족) |

> 위 값은 *그 하네스 레포가 공표한 사실*이고, 상세·최신은 언제나 레포가 원천이다. 여기 적힌 것과 레포가 어긋나면 **레포가 맞다** — 카탈로그 행을 PR로 고친다.

## 3. 행 스키마 (새 하네스를 추가할 때)

새 하네스는 §2 표에 **아래 8열을 채운 한 행**을 더한다. 그 이상 쓰지 않는다 — 설치 절차·옵션·트러블슈팅은 하네스 레포 몫이다(§1.1).

| 열 | 무엇을 적나 | 적지 않는 것 |
|---|---|---|
| 하네스 | 식별자(레포명) | — |
| 무엇을 하나 | 한두 문장. *왜 붙이는지*가 보이게 | 아키텍처 설명 |
| 레포 URL | 온보딩 지식의 단일 원천 — **S9.5-a가 이 URL로 클론한다** | — |
| **온보딩 룰북 경로** | 레포 안에서 *설치 절차를 소유한 문서*의 **레포 루트 기준 경로**. **S9.5-a가 이 경로의 룰북을 서브에 실어** 설치 대화를 위임한다 — 이 한 칸이 있어 하네스가 절차를 바꿔도 프레임워크는 그대로다 | 룰북 본문·절차 요약 (복제 금지 — 즉시 낡는다) |
| 진입 방법 | 룰북이 태우는 **진입점 한 줄** (마법사·설치 커맨드 등) | 옵션·플래그 전량, config 스키마 |
| 최초 설치자 경로 | 온보딩이 성사됐을 때 **인스턴스에 기록할 좌표**(대개 대시보드 URL) + 특기사항 | 단계별 절차 복제 |
| 합류자 경로 | 이미 도는 하네스에 사람이 합류할 때 할 일 (대개 *로컬 할 일 없음* + 대시보드 등록) | — |
| 전제조건 | 없으면 붙일 수 없는 것 (런타임·플랫폼 제약·도달성). **도달성은 *하네스가 실행되는 런타임 컨텍스트* 기준으로 적는다** — 설치를 돌린 사람의 머신이 아니라 실제 소비자가 기준이다 | 권장 사양 |

**금지**: 토큰·키·엔드포인트 등 **배포별 구체값**을 카탈로그에 박지 않는다. 그런 값은 인스턴스(Layer 1) 또는 머신 로컬 시크릿에 산다 (자격증명 경계 / POLICY-TRACKING).

## 4. SETTER 연계 (두 지점) — 요약

상세는 `agents/SETTER.md`. 여기서는 본 카탈로그가 *어디서 소비되는지*만 정리한다.

| 지점 | 하는 일 | 조건부 |
|---|---|---|
| **S5.9** (인터뷰 페이즈) | "하네스를 쓸 건가 · 어느 것인가"만 수집. 다른 인터뷰가 전부 그 자리에 있으므로 일관된다 | "아니오"면 S9.5까지 통째로 스킵 |
| **S9.5** (검증 S9 이후 · 종료 S10 이전) | 선택했고 **팀 최초 설치자면** — **S9.5-a**(SETTER): 레포 클론·**온보딩 룰북 실재 확인**·디스패치 패키지 조립 → **S9.5-b**(오케스트레이터): 그 룰북을 **서브로 띄워**(4-튜플) 설치 대화 진행 → 지상검증 → 대시보드 좌표를 인스턴스에 기록·커밋·push | 합류자는 **no-op** |

**S9 이후에 두는 이유 (배치 근거)**:
1. 하네스 온보딩은 **`dlc-meta` 공유 원격 URL이 확정·검증된 상태**를 입력으로 받는다 — 그 검증이 끝나는 곳이 S8.6(push)·S9(체크)다.
2. S9 뒤라는 것은 **하네스 온보딩이 실패해도 코어 부트스트랩은 이미 성사**됐다는 뜻이다. 실패가 부트스트랩으로 번지지 않게 격리된다 — EX-15와 같은 사상(**C FALLBACK**, 중단 금지. `agents/orchestrator/ERROR-POLICY.md` §1).

**최초/합류 판정은 묻지 않는다** — SETTER Q2.4가 *원격에 인스턴스가 있느냐*로 신규/합류를 가르는 것과 같은 방식으로, **시스템 인스턴스에 그 하네스의 대시보드 좌표가 기록돼 있느냐**로 가른다.

| 인스턴스 「부착된 하네스」 섹션 | 판정 | 행동 |
|---|---|---|
| 해당 하네스 기록 **있음** | 팀에서 이미 돌고 있다 | **no-op** — 합류자는 로컬에서 할 일이 없다. 기록된 대시보드로 가면 된다 |
| 기록 **없음** | 아직 아무도 안 붙였다 → **최초 설치자** | 카탈로그 행 그대로 안내 → 성사 시 좌표 기록·커밋·push |

기록이 커밋되면 **합류자는 clone만으로 그 값을 손에 넣는다** — 입력도 안내도 불필요하다. 그래서 최초 설치자의 기록·push 성사가 중요하다 (POLICY-TRACKING).

## 변경 이력

본 카탈로그 v1.0 — 선택적 외부 하네스의 *목록화*와 SETTER 2지점(S5.9·S9.5) 연계 도입. 새 POLICY-* 라벨은 만들지 않았다 — 프레임워크가 갖는 것은 *목록과 안내 게이트*뿐이고 상태 기계·횡단 규율이 없기 때문이다(선례: 축적 지식 원천 S5.8도 라벨을 만들지 않았다).

v1.1 — 행 스키마에 **「온보딩 룰북 경로」** 칸 추가(7열→8열)로 S9.5를 *안내*에서 **위임 실행**으로 올렸다. 프레임워크는 여전히 절차를 복제하지 않는다 — 늘어난 것은 *포인터 한 칸*이고, 실행은 그 룰북을 실은 서브가 한다. 새 에이전트 파일·새 POLICY-* 라벨도 만들지 않았다(기존 서브 호출 계약 §3.2 4-튜플과 C FALLBACK을 그대로 쓴다).

v1.2 — 「전제조건」의 **도달성 기준을 정정**: *배포 호스트*가 아니라 **하네스가 실제로 실행되는 런타임 컨텍스트**(컨테이너로 도는 하네스면 그 컨테이너 안)가 기준이다. §3 행 스키마에도 같은 기준을 명시. 문구 정정이며 규율 변경은 아니다 — 일반 HTTPS 원격이면 양쪽 모두 도달하므로 실제 판정 결과는 대개 같다.

향후 변경은 깃 PR/머지 (원칙 8) — 하네스 추가는 §2 표에 **행 하나**.
